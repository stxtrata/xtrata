# Plan: proposals 28 and 29

**28** — Explore: search, filter, and the facts a spectator needs
**29** — Which game am I watching, and is it my move somewhere else

Written 2026-08-13, after re-reading the code rather than the proposals. Three
things have changed since those were drafted, and one of them changes what can
be built at all.

---

## What is already done

**Proposal 14 landed most of 28's foundation** (`e418b97c`). The list already:

- carries `mine: 'your-move' | 'waiting' | null` and `seat: 'open' | null` on
  every row, computed from `checkSender` — the same pure function that decides
  who may actually move, so there is one rule and not a copy;
- gates the badge on rules being confirmed **and** the game still being live;
- sorts actionable rows first, stably;
- rebuilds on connect, because every answer depends on who is asking;
- says the window is the newest 25 and that the order depends on the viewer;
- reads at most four pages per game (`EXPLORE_ENTRY_LIMIT`), and past that
  declines to state a position it has not seen all of.

**Proposal 29's title work is half-built already.** `flashTitle` exists
(`app.ts:1428`): it prefixes `(your turn)` on a turn or check event and restores
on `visibilitychange`. What it does *not* do is say **which game** — `baseTitle`
is whatever the document was called, so every tab still looks identical, which is
exactly the complaint.

**`listeningInBackground()` already exists** and gates hidden-tab polling on
three conditions: background listening asked for, a game loaded, and that game
live. The cross-game watcher needs the same shape and should reuse the thinking.

## The finding that changes proposal 28

> "Sponsorship details including who and how much and what remains for each
> sponsored player etc."

**This cannot be built as asked, and the reason is in the contract.**

`get-sponsorship` takes **`(game uint, who principal)`**. It answers about one
player on one game. There is no function that lists the sponsorships on a game,
and no event index to walk — so *"each sponsored player"* is not a question the
chain can be asked at all. You can only ask about somebody you already know the
name of.

That leaves three honest options, and they are not equivalent:

| where | cost | what it can say |
|---|---|---|
| **A. The game view** (already has a panel) | zero extra — it already reads this | Everything, for the connected player, including the expiry nothing currently reads |
| **B. Explore, own rows only** | **one read per row you are in** | Your own sponsorship on your own games |
| **C. Explore, every player** | **impossible** | — |

**Recommendation: A, and only A.** The panel already reads exactly this row and
already caches it per `game|address`. Adding the expiry costs nothing and closes
the more serious gap: **no file in `packages/ui/` reads `SponsorshipRow.expiry`
at all**, despite `client.ts` decoding it — so no player has ever been told that
their reserve expires, or when.

That matters more than a column in a list. A sponsorship expires ~15 hours after
funding, and once expired **any principal may settle it**, after which the
beneficiary can never be sponsored on that game again. A player who cannot see a
countdown cannot protect a game they are still playing. See `ops/RUNBOOK.md`.

**If B is wanted anyway**, it must be opt-in per row — an expand — never on the
list build, or the zero-extra-reads property that proposal 14 established is lost.

## The finding that shapes proposal 29

The cross-game watcher is **the only thing in this entire review that wants to
spend more request budget.** Proposals 7 and 19 are both about spending less, and
proposal 7 landed a three-wide pool and removed an eighteen-request boot
specifically to stop the board starving its own wallet.

So the watcher is built against a **fixed ceiling asserted in a test**, not
against a hope. The rules it must obey, all of which have precedent in this
codebase:

1. **Only when connected.** No address, no watching. There is no "you" to answer
   for.
2. **Only the background rate**, never the foreground one.
3. **Only live games this player can act in**, capped at a small number.
4. **Never while a wallet dialog is open** (ADR-0011 decision 4).
5. **Announce once per state change, and never again for the same state.** This
   is the same anti-spam property proposal 21 needs for its screen-reader
   announcer — build it once, in one place, and let both use it.

And the limit to state plainly, in the UI and not only here: **with no server
there are no push notifications.** A tab must be open. What is achievable is
"this open tab also watches your other games", not "your phone buzzes".

## The work

### 28, in four steps

Each step is independently shippable and independently testable. Stop after any
of them and the board is still coherent.

**28a — Filters.** `mine`, `open seat`, `live`, `finished`, `ranked`, plus `all`.
Every one reads a field the row already carries, so this is presentation only and
costs nothing. Buttons in the Explore header, one pressed at a time,
`aria-pressed` on each.
*Risk: none. It cannot read the chain.*

**28b — Search by game number.** A number inside the loaded window filters
locally. A number **outside** it does one direct `getGame`, and the row says how
it was found — a search that silently only searches the visible page is worse
than no search. Bounded to exactly one lookup; no walking.
*Risk: the one place in 28 that can spend a read. Bound it in code, assert the
bound in a test.*

**28c — Search by player, honestly scoped.** Filters the loaded window only, and
**says so**, because finding every game a principal has played needs a walk of
the whole contract and there is no index. Overclaiming here would be worse than
the feature.
*Risk: none, if the scope is stated. Real risk if it is not.*

**28d — Creator by name.** `Names.peek` for anything already resolved, and add
the openers to the batch `resolveAll` the board already runs. Openers repeat
heavily, so this is a handful of lookups through the existing three-wide pool.
*Risk: low. It must never block the row from rendering — the existing resolvers
already never do.*

**Plus the sponsorship expiry on the game view**, which is where it belongs: a
countdown in the panel, derived from `getHeight` and `BlockTimes`, saying when
this reserve can be settled by anybody.

### 29, in three steps

**29a — The tab says which game.** `document.title` becomes
`Game 8 · black to move · X Chess`, restored on leaving. `flashTitle` keeps
working on top of it, and its `baseTitle` capture has to move, or the flash will
restore a stale title.
*Risk: low, but it interacts with existing code — the ordering of `baseTitle`
capture is the thing to get right.*

**29b — Announce once.** Extract the change-gate that decides whether a state is
new, so 29 and proposal 21 share one implementation. Ten polls with no change
produce nothing.
*Risk: none, and it makes 21 cheaper later.*

**29c — The cross-game watcher.** From the connected address, take the games the
list already knows this player can act in, cap the list, and poll only those, only
at the background rate, only while the four gates above hold. On a turn: the
Explore badge already exists, the title changes, and the existing sound plays.
*Risk: the highest in either proposal. It is the only thing that increases read
volume, and it does so on a tab nobody is looking at.*

## Testing

Every harness needed already exists. Nothing here needs a new kind of test.

| what | where | the assertion that matters |
|---|---|---|
| 28a filters | `tests/e2e/explore.test.ts` | Filtering to *mine* shows only games `checkSender` admits — not a second copy of the rule |
| 28a, no wallet | same | The *mine* filter is **absent**, not empty |
| 28b search in window | same | Zero chain reads |
| 28b search outside | `tests/e2e/request-budget.test.ts` | **Exactly one** `getGame`, and the row says how it was found |
| 28c player search | `tests/e2e/explore.test.ts` | The scope is stated on screen |
| 28d creator name | same | A row renders before any name resolves |
| **28, overall** | `tests/e2e/request-budget.test.ts` | Filtering and searching add **zero** reads over the existing burst. *If this is hard to write, the feature is built wrong.* |
| expiry countdown | `tests/e2e/` | Rendered as a duration, never a block height; a sponsorship in its last hour says so |
| 29a title | `tests/e2e/` | It **changes when the turn changes** — assert the change, not the initial value |
| 29a + flash | same | A turn flash still restores the right title, not a stale one |
| 29b announce-once | same | Ten poll ticks with no change produce no sound and no title churn |
| 29c watch list | same | Only games the connected address is in; **nothing at all** with no wallet |
| **29c budget** | `tests/e2e/request-budget.test.ts` | Per-tick reads against a **fixed ceiling** with four games watched. Not "reasonable" — a number |
| 29c dialog | same | No read while `intent.state === 'signing'` |

**Two properties to write as failing tests first**, because both are the kind
that pass for the wrong reason:

- *Silence when nothing changed.* Trivially true if the watcher never runs. Drive
  a real state change first, prove it speaks, then prove it goes quiet.
- *The read ceiling.* Assert it with several games loaded, or one game passes a
  ceiling meant for four.

## Order, and why

```
28a  filters            no reads, presentation only
28b  number search      one bounded read
28d  creator names      existing pool
28c  player search      scoped and stated
     ── sponsorship expiry on the game view ──
29a  title identity
29b  announce-once      shared with proposal 21
29c  cross-game watcher the only read-volume increase
```

**28 before 29** because 29c watches the games 28 makes navigable, and because
every step of 28 is safer than any step of 29.

**The expiry work sits between them** deliberately. It is the highest-value item
in either proposal — nobody has ever been told their reserve expires — and it
belongs to neither, which is exactly how it went unbuilt.

**29c last**, and it is the one to be willing to abandon. If the read ceiling
cannot be met with the budget the board has, the honest outcome is 29a and 29b
without it: the tab tells you which game you are in, and the Explore badge tells
you where you owe a move when you look. That is most of the value for none of the
risk.

## What is deliberately not in this plan

- **Sponsorship for every player in the list.** The chain cannot be asked.
- **Push notifications.** No server. Say so in the UI rather than implying
  otherwise.
- **Searching every game a player has played.** Needs a walk of the whole
  contract with no index. The scoped version says what it covers.
- **Saved searches, a notification centre, a history sidebar.** Each is the
  obvious richer version of a step above, and every byte is permanent.
