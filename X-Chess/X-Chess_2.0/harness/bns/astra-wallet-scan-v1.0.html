Access is checked before every scan and retry. An API key is sent only to Hiro via x-api-key. A failed wallet request gets one short retry, then moves aside so other wallets can continue. Deferred checks return automatically after increasing delays. Five consecutive failures trigger a provider cooldown; confirmed 429s always pause requests. Connection failures trigger temporary cooldowns without permanently reducing request speed. Confirmed 429 responses reduce speed; five successful calls begin restoring it. Keyed requests target at most 300 calls/minute before latency and server limits. Invalid keys, exhausted monthly quotas and permanent API errors need attention. Stop always pauses until you resume.

04 / Prepare safely
This app cannot execute consolidation. It exports a draft checklist. Scanning a phrase does not connect a signing wallet or prove that you can spend from every discovered address.
Build a draft plan to check preparation requirements.
    

    

    

    

    

    These confirmations are your statements, not automated proof. Changing the selection, plan or inputs resets them. Preparation requires selected Stacks balance and NFT checks from the last 15 minutes; this does not guarantee execution-time freshness.
    


    1. Prepare: complete the scan for the intended wallets, review exclusions, choose the destination and verify access to each signing account.
    2. Fund fees: send only the reviewed STX top-ups. Wait for successful confirmation and verify each source received its funding.
    3. Move assets: transfer the selected tokens, NFTs and BNS names with the correct contract method. Check each transaction succeeded and the destination actually received each asset.
    4. Move remaining STX last: only after that source’s asset transfers succeed, fetch its balance again and deduct the live sweep fee.
    5. Reconcile: check the destination and every source against the checklist. Record failures and excluded assets; an empty source alone does not prove delivery.
    

    A future automated executor must enforce these steps with transaction IDs, current fees, nonce management, contract validation, asset-specific post-conditions, confirmed receipts and restart-safe records. A pending or failed transaction must block dependent steps. User checkboxes cannot replace these checks.
    

    Coverage, privacy & how to complete a consolidation
    BTC discovery is enabled for new phrase scans by default. Previously saved Stacks-only snapshots cannot reconstruct Bitcoin addresses: re-derive with Bitcoin enabled. Per-wallet and aggregate amounts are observed holdings, not spendable estimates. sBTC and USDCx are matched to their exact mainnet asset identifiers; every other fungible token remains listed with its exact base-unit balance.
    Discovery covers only the chosen indices and paths, not every possible account. Stacks holdings come from Hiro's indexed confirmed data; NFT pages are read until complete. Each check has its own timestamp. Resume reuses completed checks, Refresh stale invalidates only selected checks older than your threshold, and Refresh all repeats the selected checks. Browser-local storage may be unavailable or cleared; always keep a snapshot backup. BNS-V2 is identified by its exact contract; other name contracts remain visible as NFTs. Unresolved names retain their token IDs. Token quantities are exported as exact base-unit strings. Unknown or failed reads remain incomplete.
    The planner counts one transfer per NFT and nonzero fungible-token balance. It excludes locked STX and blocks incomplete Stacks reads. Contract-specific restrictions, pending transactions and fee changes require a fresh check in your signing wallet. Bitcoin is inventory only: its UTXOs are not classified for inscriptions or runes, so this page does not propose BTC sweeps.
    1. Refresh sources and destination before execution; verify that you control the new address.
    2. Review each asset's transfer function and restrictions in your signing wallet.
    3. Fund fee shortfalls from the appointed funder and wait for confirmation.
    4. Transfer assets, verify successful on-chain receipts, then sweep remaining available STX.
    5. Refresh this inventory and inspect the destination; a source balance decrease alone does not prove receipt.
    Snapshots include public addresses, derivation paths and holdings, but never a phrase, key, BIP39 passphrase or API key. JavaScript cannot guarantee erasure of all memory copies; clearing the session and closing the tab ends its use here.
