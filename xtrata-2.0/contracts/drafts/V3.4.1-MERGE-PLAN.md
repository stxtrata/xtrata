# Building v3.4.1: what to take from v3.2.4, what to leave

**Who this is for:** Jim, deciding what goes in. Written to be read without knowing Clarity.

**The plan in one line:** start from v3.4.0, but throw away its migration and keep the one
that is already live, add the recipient parameter from v3.2.4, ship as v3.4.1.

> **Revised.** An earlier version of this document recommended v3.4.0's migration. That was
> wrong, and Jim's objection is the reason. See section 4.

---

## 1. The situation in plain terms

You have two unshipped contracts. Both start from the same v3.2.3 that is live on mainnet
today. Neither knows about the other, because they were written three weeks apart by
different pieces of work.

| | v3.4.0 | v3.2.4 |
|---|---|---|
| Written | 2 July | 27 July |
| What it is about | A different way to move old inscriptions onto the new contract | Letting one person pay for someone else's inscription |
| Deployed | No | No |

The version numbers are misleading. 3.4.0 is the **older** one despite the higher number.

## 3. Item A: the thing DeOrganized is waiting for

**The problem today.** The contract charges the fee to whoever sent the transaction, and
gives the inscription to that same person. Payer and owner are welded together. There is no
way to say "I will pay, but give it to her."

**What v3.2.4 adds.** Three new ways to mint, each a copy of an existing one with a
recipient added:

| Existing, unchanged | New version |
|---|---|
| `mint-single-tx` | `mint-single-tx-to` |
| `mint-single-tx-recursive` | `mint-single-tx-recursive-to` |
| `mint-single-tx-with-relationships` | `mint-single-tx-with-relationships-to` |

**Who ends up as what:**

| | Normal mint | The new `-to` mint |
|---|---|---|
| Pays the fee | The sender | The sender |
| Owns the inscription | The sender | **The named recipient** |
| Recorded as the creator | The sender | **The named recipient** |
| Shows as "payer" in the event log | The sender | The sender |

The recipient becomes both owner **and** creator, which is better than DeOrganized asked
for. Their writer gets full on-chain authorship, the platform pays, and the platform appears
only as a footnote in the event log.

Nothing breaks. The three original functions still behave exactly as they do now.

## 4. Item B: migration, reconsidered

**You objected that v3.4.0's migration doubles the data. You are right, and it is worse than
it first looks.**

### The two approaches

**How the live contract does it today** (and how v3.2.4 does it): copy the *description* of
the inscription across, leave the content where it is. When someone asks the new contract
for the content, the new contract quietly fetches it from the old one and hands it back. The
caller never knows the difference.

**How v3.4.0 does it:** the person migrating **uploads the entire content again**. The
contract re-checks the hash to prove it is the same content, then mints at the same ID.

### Why v3.4.0's version is the wrong trade for Xtrata

| | Live approach | v3.4.0 approach |
|---|---|---|
| Bytes stored on chain | Once | **Twice** |
| Cost to migrate one inscription | 0.1 STX | A full mint fee, scaling with size |
| Cost to migrate a 128 MiB piece | 0.1 STX | The same as inscribing it from scratch |
| Needs a copy of the original content | No | Yes |
| Proven in production | **Yes, 5 times** | Never run |

Xtrata's entire proposition is that the data is on chain permanently. Writing the same bytes
a second time is not a neutral implementation detail, it is paying twice for the thing you
sell, and it makes the chain carry duplicate copies of every migrated piece forever.

### The argument I made for v3.4.0, and why it does not hold

I recommended it because its migration is **generic**. You add a new source contract with one
admin call instead of writing a new function and deploying a new core. That avoids a
treadmill: hardcode a source, need another, deploy again.

Two things kill that argument.

**First, you are ending the treadmill a different way.** You said this should be one of the
last core contracts. If that holds, the list of contracts anyone will ever migrate *from* is
already closed and it is three long: v1-1-1, v2-1-0, v3-2-3. There is no fourth to add later.
A mechanism for adding sources you will never add buys nothing.

**Second, the generic version cannot actually give you transparent reads without the
re-upload.** This is a Clarity limitation, not a design choice. To call out to another
contract dynamically, the contract must be handed to you as a function argument. It cannot be
looked up from a stored record. So `get-chunk(id, index)` has no way to discover "this token
came from over there" and fetch it. Only hardcoded names work in a reader.

That is precisely why the live contract hardcodes `.xtrata-v1-1-1` and `.xtrata-v2-1-0`, and
why v3.4.0 has no proxy at all. v3.4.0 does not skip the proxy by cleverness. It skips it
because it cannot have one, and re-uploading is the price it pays for that.

### The three properties, and why you cannot have all of them

| Approach | Data stored once | Add sources without redeploying | Content reads just work |
|---|---|---|---|
| Live v3.2.3 and v3.2.4 | **Yes** | No | **Yes** |
| v3.4.0 | No | Yes | Yes |
| Allowlist plus a reader that takes the source as an argument | Yes | Yes | No, every caller must pass the source in |

Your priorities are data-once and fewer deploys. The middle column is the one you are solving
outside the contract by stopping. So the top row is the right one.

**Verdict: keep the migration that is already live and proven. Drop v3.4.0's entirely.**

That means v3.4.1's migration is v3.2.3's, extended by one source.

## 5. Item C: the gap that has to be closed

The live contract knows how to fetch content from v1 and v2. It has never needed to fetch
from v3.2.3, because v3.2.3 is itself the live contract.

v3.2.4 added a `migrate-from-v3-2-3` function but **nobody taught the content-fetching helper
about v3.2.3**. So a v3.2.3 inscription migrated onto v3.2.4 would exist, look correct, and
return nothing at all when asked for its content.

In v3.4.1 that helper needs all three names in it:

| Source | In the live contract | Needed in v3.4.1 |
|---|---|---|
| `.xtrata-v1-1-1` | Yes | Yes |
| `.xtrata-v2-1-0` | Yes | Yes |
| `.xtrata-v3-2-3` | Not needed | **Yes, and currently missing** |

This is a small change, but it is the difference between migration working and migration
silently losing access to content. **Test it by migrating a token and immediately reading
chunk zero back.**

### One consequence to accept knowingly

Keeping the proxy means v3.4.1 permanently depends on v3.2.3 remaining readable on chain.
That is fine. Contracts on Stacks are immutable and cannot be removed, and reading an old
contract costs nothing. But it is worth saying out loud: the old cores never go away, they
become the storage layer for anything migrated off them.

That is the direct consequence of storing the data once, and it is the right trade.

## 6. A question worth asking: does v3.4.1 need migration at all?

Since the goal is a smaller, final core, it is worth checking whether this feature earns its
place.

**Evidence for keeping it:** migration has genuinely been used. Five calls found on the live
contract, all `migrate-from-v1` and `migrate-from-v2-1-0`. It works and people use it.

**Evidence for dropping it:** five calls out of 1,224 transactions is under half a percent.
The app already resolves tokens across contract versions, so old inscriptions remain visible
and readable whether or not they are migrated.

**What migration actually buys** is a single unified collection. Migrated tokens live under
one contract, so marketplaces and wallets show them as one set rather than four.

**My recommendation: keep it.** It is already written, it is proven, and unifying the
collection is a real product benefit as the number of inscriptions grows. But if you want the
smallest possible final core, dropping migration entirely is a legitimate option and I would
not argue hard against it. Flagged so it is a decision rather than an assumption.

## 7. The other defect: the version string

| Contract | Reports itself as | Correct? |
|---|---|---|
| v3.4.0 | `xtrata-v3.4.0` | Right for 3.4.0, wrong for 3.4.1 |
| v3.2.4 | `xtrata-v3.2.3` | **Simply wrong** |

Integrators read this string to confirm which contract they are talking to. DeOrganized does
exactly this. It must say `xtrata-v3.4.1`.

## 8. Item F: the fee question you raised

You said a promise you have to remember is the wrong mechanism. Agreed.

**Already true on the live contract**, and worth telling DeOrganized because nobody has:

| Protection | Value |
|---|---|
| Absolute ceiling on any fee unit | 1 STX. The transaction simply fails above it |
| Most a fee can rise in one change | Double |
| Most a fee can fall in one change | To one tenth |

From today's 0.01 STX it would take seven separate transactions to reach the ceiling.

**What is missing:** a change lands the instant you send it. Nobody sees it coming, and you
cannot take back a mistake.

**Proposed:**

| Change | Effect |
|---|---|
| Fee **increases** happen in two steps: propose, then confirm after a wait | You cannot fat-finger a rise. Integrators get warning |
| Fee **decreases** stay instant | A price cut needs no ceremony |
| A cancel button, and a way to read the pending change | Anyone can ask the contract "is a change coming, and when" |
| Emergency route unchanged | If something genuinely goes wrong, pause. Do not price-gouge in a hurry |

The wait would be counted in Bitcoin blocks, roughly 144 a day, so a week is about 1008.

The third row answers DeOrganized's actual question, because it makes the notice period
machine-readable and stops it depending on you remembering to post.

**This is the only item with real effort attached.** Fine to ship v3.4.1 without it.

## 9. What you end up with

| | Comes from | Status |
|---|---|---|
| Chunking, hashing, sealing, fees, pausing, the allowlist | v3.2.3, unchanged in both | No decision needed |
| Migration that stores data once | v3.2.3, already live | Carry forward, plus the v3.2.3 source |
| Pay for someone else's inscription | v3.2.4 | Port across |
| 128 MiB ceiling | v3.2.4 | One number |
| Correct version string | new | Trivial |
| Fee timelock | new | Optional |
| ~~Re-upload migration~~ | ~~v3.4.0~~ | **Dropped. Doubles the data** |

Worth noticing: once v3.4.0's migration is removed, **almost nothing of v3.4.0 remains**. Its
migration was the only substantial thing it added. So v3.4.1 is closer to "v3.2.4, fixed"
than to "v3.4.0 plus extras". The name is a courtesy to the version numbering, not a
description of the lineage.
