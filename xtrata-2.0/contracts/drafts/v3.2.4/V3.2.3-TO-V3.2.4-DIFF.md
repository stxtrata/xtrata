**Compared:**

| | File | Status |
|---|---|---|

## 0. Read this first: v3.4.0 is not the successor to v3.2.4

The version numbers lie. `contracts/live/` and `contracts/clarinet/` both contain an
`xtrata-v3.4.0.clar`, and 3.4.0 is a higher number than 3.2.4, so the natural assumption is
that 3.4.0 came later and supersedes it. It did not.

| | v3.4.0 | v3.2.4 candidate |
|---|---|---|
| First committed | **2026-07-02**, in the bulk `xtrata 2.0 created as optimised version` commit | **2026-07-27**, three weeks later |
| Branched from | v3.2.3 | v3.2.3 |
| Contains the other's changes | No | No |
| `mint-single-tx-to` (payer is not owner) | **Absent** | Present |
| `MAX-TOTAL-CHUNKS` | 2048 | 8192 |
| Migration functions | `migrate-single-tx`, `migrate-staged`, `set-migration-source` | `migrate-from-v3-2-3` |
| Keeps `migrate-from-v1`, `migrate-from-v2-1-0` | No, removed | Yes |
| Extra constants | `SELF`, `ERR-MIGRATION-SOURCE` | none |
| `get-contract-info` version string | `"xtrata-v3.4.0"`, correct | `"xtrata-v3.2.3"`, **wrong** |
| Trait variants present | mainnet, clarinet, testnet | mainnet only |
| Deployed anywhere | No. 404 on mainnet and testnet | No. 404 on mainnet and testnet |

**These are two divergent branches off v3.2.3, and neither one contains the other.** They
are also about different things. v3.4.0 is a migration release. v3.2.4 is the payer and
recipient release written specifically for the DeOrganized use case.

Only `xtrata-v3-2-3` is actually deployed. `contracts/live/` means "deployment ready", not
"currently on chain".

The three copies of v3.4.0 (`live/`, `clarinet/contracts/`, `other/`) are the same contract
differing only in the `impl-trait` line: mainnet, local clarinet, and testnet respectively.
That is normal, not drift.

### Are they effectively the same contract?

No. They share a common core and differ in two orthogonal feature areas, plus one
architectural choice that matters more than either.

**Shared, identical in both:** chunking and the incremental SHA-256 chain, all five fee
units and their formulas, the fee guards, every quote function, begin/add-chunk/seal,
pause, allowlist, admin and ownership transfer, and the no-idempotency posture on mint.
That is most of the contract.

**Different:**

| | v3.2.4 | v3.4.0 |
|---|---|---|
| Payer is not owner | `mint-single-tx-to` and two variants | Absent. Mints to `tx-sender` |
| Event `payer` field | Present | Absent |
| Migration design | **Hardcoded.** One function per source (`migrate-from-v1`, `migrate-from-v2-1-0`, `migrate-from-v3-2-3`), each with a literal contract reference | **Generic.** `legacy-inscription-trait` plus an `AllowedMigrationSources` allowlist and `set-migration-source` |
| Adding a future migration source | Needs a new contract version | Owner call, no redeploy |
| Chunk proxy for migrated tokens | Yes, for v1 and v2. Broken for v3.2.3 | Not present |
| `MAX-TOTAL-CHUNKS` | 8192 | 2048 |
| `set-next-id` returns | `(ok true)` | `(ok value)` |
| `SELF` / `current-contract` | Not used | Used |
| Version string | Wrong | Correct |

400 lines of code difference across 34 hunks, out of roughly 1300 to 1400 code lines each.

The architectural point: **v3.4.0's trait-based migration is the better design.** Hardcoding
a migration function per source is what forces a new contract version every time something
needs migrating, which is exactly the treadmill v3.2.4 is standing on. v3.4.0 makes adding
a source an owner call.

The feature point: **only v3.2.4 answers DeOrganized.**

So neither is shippable as-is for this purpose. The obvious move is v3.4.0's migration
architecture plus v3.2.4's recipient parameter, which is a merge rather than a pick.

### What this means for the rest of this document

Nothing below changes. It compares deployed v3.2.3 against the v3.2.4 candidate, and both
are correctly identified. Every number stands.

But **v3.2.4 is the only contract in the repo that answers DeOrganized issue #1.** If
v3.4.0 ships instead, the recipient parameter does not exist and the payer and owner are
still welded together. Something has to reconcile these two branches before either goes to
mainnet, because the version rule for this project is newest contract only, with old
versions reached by migration rather than a second registry entry.

That reconciliation is an open decision, not something this document settles.

## 1. Everything that changed, at a glance

| # | Change | Kind | Breaks anything? | Who cares |

| 1 | `mint-single-tx-to` and two variants added | New functions | No | DeOrganized. This is their issue #1 |

**Verdict: fully backward compatible.** No function was removed, renamed, or had its
signature changed. No constant, data-var, map, or private function was removed or renamed.
Every existing call site keeps working with identical behaviour.

## 2. Change 1: payer and owner can differ

The headline. Three new public functions, each the existing one with `recipient` bolted on
the front.

| Existing (unchanged) | New sibling |
|---|---|
| `mint-single-tx` | `mint-single-tx-to` |
| `mint-single-tx-recursive` | `mint-single-tx-recursive-to` |
| `mint-single-tx-with-relationships` | `mint-single-tx-with-relationships-to` |

`recipient` is the **first** argument on the new ones. Everything after it is identical to
the original.

```clarity
(define-public (mint-single-tx-to
  (recipient principal)          ;; <- new, first
  (expected-hash (buff 32))
  (mime (string-ascii 64))
  (total-size uint)
  (chunks (list 32 (buff 16384)))
  (token-uri-string (string-ascii 256))
)
```

### Who ends up as what

This is the part worth reading twice.

| Role | `mint-single-tx` | `mint-single-tx-to` |
|---|---|---|
| Pays the protocol fee | `tx-sender` | `tx-sender` |
| Pays the miner fee | `tx-sender` | `tx-sender` |
| NFT owner | `tx-sender` | **`recipient`** |
| On-chain `creator` | `tx-sender` | **`recipient`** |
| Recorded in the event as `payer` | `tx-sender` | `tx-sender` |

The recipient becomes **both owner and creator**. The payer is credited nowhere in the
inscription metadata and appears only as the `payer` field on the emitted event.

For a publisher paying for a writer's piece, that is the correct outcome. The writer holds
full on-chain provenance. The platform's involvement is visible in the event log and
nowhere else.

There is no authorisation check on `recipient`. Anyone can mint to anyone. The only cost
of doing so is paying for it, so there is no griefing vector beyond gifting someone an NFT.

### Backward compatibility, mechanically

The old three now delegate to a shared internal with `tx-sender` passed as the recipient:

```clarity
(mint-single-tx-internal ... (list) (list) tx-sender)
```

So calling `mint-single-tx` on v3.2.4 does exactly what it does on v3.2.3.

### The staged path did not change

`seal-inscription`, `seal-inscription-batch`, `seal-recursive` and
`seal-with-relationships` all pass `tx-sender` as both creator and recipient. There is no
`seal-to`. Staged uploads still mint to whoever seals them.

## 4. Change 3: the `inscription-sealed` event

One field added. Nothing removed, nothing renamed, no reordering that matters.

| Field | v3.2.3 | v3.2.4 |
|---|---|---|
| `event` | `"inscription-sealed"` | same |
| `token-id` | yes | same |
| `owner` | the minter | **the recipient** |
| `payer` | absent | **new. the principal that paid** |
| `token-uri`, `final-hash`, `chunk-size`, `total-size`, `total-chunks`, `dependencies`, `parents` | yes | same |

An existing indexer that reads `owner` keeps working. On a plain `mint-single-tx` the two
fields are equal, so nothing appears to change. They only diverge on a `-to` call.

New event in v3.2.4: `inscription-migrated`, with `token-id`, `source-contract`,
`source-id`, `owner`.

## 5. Change 4: size ceiling raised 4x

| Constant | v3.2.3 | v3.2.4 |
|---|---|---|
| `MAX-TOTAL-CHUNKS` | 2048 | **8192** |
| `MAX-TOTAL-SIZE` (derived) | 33,554,432 bytes (32 MiB) | **134,217,728 bytes (128 MiB)** |
| `CHUNK-SIZE` | 16384 | unchanged |
| `MAX-SINGLE-TX-CHUNKS` | 32 | unchanged |
| `MAX-UPLOAD-BATCH-SIZE` | 32 | unchanged |

This is a raise, so nothing that fit before stops fitting. Only the staged path can reach
these sizes. Single-tx is still capped at 32 chunks, which is 512 KiB.

`get-contract-info` reports both values, so an integrator reading limits at runtime picks
this up for free.

## 6. Change 5: `migrate-from-v3-2-3`

Lets a holder move an existing v3.2.3 inscription onto v3.2.4 while **keeping the same
token-id**.

| Property | Behaviour |
|---|---|
| Argument | `token-id` on the old contract |
| Cost | `begin-fee-unit`, currently 100,000 microSTX (0.1 STX) |
| Who can call it | The current owner. The contract transfers the source token, which requires ownership |
| Token-id | Preserved |
| Old token | Transferred to the v3.2.4 contract itself, not burned |
| `creator` | Copied from the source. Original creator survives |
| `owner` | Set to `tx-sender`, the migrator |
| Copied across | `mime-type`, `total-size`, `total-chunks`, `final-hash`, token URI, dependencies, parents |
| Marked `sealed` | Always true |
| Guard | `ERR-DUPLICATE` if that token-id already exists on v3.2.4 |
| Provenance | `record-migration-source` points back to `.xtrata-v3-2-3` and the source id |

Chunk data is **not** copied. Only metadata, the hash, the URI, and relationships.

That is by design. `get-chunk` on v3.2.4 falls back through the `MigrationSource` map and
proxies the read to the source contract, so content stays readable through the normal
reader without duplicating bytes on chain. For v1 and v2 tokens, that works.

**For v3.2.3 tokens it does not.** See blocker 2 below.

The reference is a bare `.xtrata-v3-2-3`, so v3.2.4 must deploy from the same address as
v3.2.3 (`SP3JNSEXAZP4BDSHV0DN3M8R3P0MY0EEBQQZX743X`) or it will not compile.

## 7. What did not change

Worth stating explicitly, because it is most of the contract and it is the reason this is a
low-risk deploy.

| Area | Status |
|---|---|
| Fee formulas (`single-tx-fee-for-chunks`, `seal-fee-for-chunks`) | Identical |
| Fee guards (`FEE-MIN` 1, `FEE-MAX` 1000000, max 2x up, max 10x down per change) | Identical |
| All five fee data-vars and their setters | Identical |
| `quote-inscription-fee`, `quote-staged-fee`, `quote-single-tx-fee` | Identical |
| Hashing (`process-chunk`, the incremental SHA-256 chain) | Identical |
| Pause, allowlist, admin, ownership transfer | Identical |
| Every read-only other than the version string | Identical |
| Dedup posture. No idempotency on the mint path, `existed` still hardcoded `false` | Identical |
| Constants, data-vars, maps, private function names | No additions, removals, or renames |

**Issue #5 is not addressed by v3.2.4.** A re-mint still succeeds with a new token-id and a
second fee. If contract-side idempotency is wanted, it is a separate piece of work.

## 8. Before this deploys

| | Item | Severity |
|---|---|---|
| 1 | **Migrated v3.2.3 tokens lose access to their content.** See below | **Blocker** |
| 2 | `get-contract-info` returns `version: "xtrata-v3.2.3"` at candidate line 1608. It must say `"xtrata-v3.2.4"` | **Blocker.** Integrators use this string to confirm which contract they are on. Shipping it wrong means a v3.2.4 contract that lies about being v3.2.3 |
| 3 | Must deploy from `SP3JNSEXAZP4BDSHV0DN3M8R3P0MY0EEBQQZX743X` for the `.xtrata-v3-2-3` reference to resolve | Blocker |
| 4 | Deploy with Clarity 3, per the deployer note. The wallet forces Clarity 4, where `as-contract` is unresolved, and `migrate-from-v3-2-3` uses `as-contract` | Blocker |
| 5 | Fee timelock work, if it is going into this version, changes the candidate again | Scope call |

### Blocker 1 in detail

`migrate-from-v3-2-3` copies no chunk data and records `.xtrata-v3-2-3` as the migration
source (candidate line 706). Content reads are meant to be rescued by the fallback in
`get-chunk`, which proxies to `get-migrated-chunk`. But `get-migrated-chunk` (line 1523)
only knows two sources:

```clarity
(if (is-eq (get source-contract source) .xtrata-v2-1-0)
  (contract-call? .xtrata-v2-1-0 get-chunk (get source-id source) index)
  (if (is-eq (get source-contract source) .xtrata-v1-1-1)
    (contract-call? .xtrata-v1-1-1 get-chunk (get source-id source) index)
    none            ;; <- every v3.2.3 migration lands here
  )
)
```

`.xtrata-v3-2-3` is not one of them, so the fallback returns `none`. `get-migrated-chunk-batch`
has the same gap and returns an empty list.

**Net effect: migrate a v3.2.3 inscription onto v3.2.4 and `get-chunk` returns `none` for
every index.** The token exists, the metadata is right, the hash is right, and the content
is unreachable through the standard reader. The bytes are not lost, they are still on
v3.2.3, but nothing on the new contract will serve them.

This is the migration path the version exists to add, so it needs a `.xtrata-v3-2-3` branch
in both helpers before deploy. Worth a test that migrates a token and then reads chunk 0
back, because the existing `xtrata-v3.2.4-sponsored.test.mjs` covers the payer and
recipient split rather than migration.

## 9. What this means for DeOrganized

| Their ask | v3.2.4 answer |
|---|---|
| Payer is not owner, in one transaction | Yes. `mint-single-tx-to` |
| Author-owned article inscriptions, platform pays | Yes, and better than asked. The author is on-chain **creator** as well as owner |
| Supporter badges minted for named members | Yes. Same function |
| Avoid mint-then-transfer orchestration | Yes. One transaction, no temp wallet, no extra ~0.03 STX per delivery |
| Their existing v3.2.3 integration | Keeps working untouched. `mint-single-tx` is unchanged |
| Fee behaviour | Unchanged. Same quotes, same numbers |
| Idempotency (their issue #5) | Not addressed. Their integrator guidance still stands |
| Larger media on their roadmap | Ceiling goes 32 MiB to 128 MiB |

Post-conditions stay on the payer, because the payer is still `tx-sender`. Their existing
`<=` post-condition pattern needs no change.
