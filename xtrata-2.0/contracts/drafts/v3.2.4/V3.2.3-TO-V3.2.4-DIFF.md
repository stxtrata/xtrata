# Xtrata v3.2.3 to v3.2.4: integration guide

**For:** developers with a contract, indexer, or client built against
`SP3JNSEXAZP4BDSHV0DN3M8R3P0MY0EEBQQZX743X.xtrata-v3-2-3`, checking what they need to
change.

**Status:** v3.2.4 is a candidate. Not deployed to mainnet or testnet at the time of
writing.

---

## 1. Short answer

**Nothing you call changes.** No function was removed, renamed, or had its signature or
return type altered. No error code changed. No fee changed. If your contract compiles and
works against v3.2.3, the same code works against v3.2.4.

Four things could still bite you, none of them in a function signature:

| | If you do this | Then |
|---|---|---|
| 1 | Compare `get-contract-info` `version` against `"xtrata-v3.2.3"` | **Breaks.** It now returns `"xtrata-v3.2.4"` |
| 2 | Parse the `inscription-sealed` event with a strict schema | **May break.** A `payer` field was added |
| 3 | Hardcode the 2048 total-chunk limit | Stale. It is now 8192 |
| 4 | Assume the payer of an inscription is also its owner | No longer guaranteed. See section 5 |

Everything else is additive.

---

## 2. What is new

Five public functions, one read-only, one map. Nothing else.

| Kind | Name | Purpose |
|---|---|---|
| public | `mint-single-tx-to` | Mint where the payer and the owner differ |
| public | `mint-single-tx-recursive-to` | Same, with dependencies |
| public | `mint-single-tx-with-relationships-to` | Same, with dependencies and parents |
| public | `set-parent-delegate` | Let a named principal attach children to your inscriptions |
| public | `migrate-from-v3-2-3` | Port a v3.2.3 inscription onto v3.2.4, keeping the token id |
| read-only | `is-parent-delegate` | Query a delegation |
| map | `ParentDelegates` | Backing store for the above |

### Signatures

```clarity
(mint-single-tx-to
  (recipient principal)              ;; NOTE: first argument
  (expected-hash (buff 32))
  (mime (string-ascii 64))
  (total-size uint)
  (chunks (list 32 (buff 16384)))
  (token-uri-string (string-ascii 256)))
  ;; -> (response { token-id: uint, existed: bool } uint)

(mint-single-tx-recursive-to        (recipient principal) ... (dependencies (list 50 uint)))
(mint-single-tx-with-relationships-to (recipient principal) ... (dependencies (list 50 uint)) (parents (list 50 uint)))

(set-parent-delegate (delegate principal) (allowed bool))   ;; -> (response bool uint)
(is-parent-delegate (owner principal) (delegate principal)) ;; -> (response bool uint)
(migrate-from-v3-2-3 (token-id uint))                       ;; -> (response uint uint)
```

`recipient` is the **first** parameter on the `-to` variants. Everything after it is
positionally identical to the function it mirrors.

There is no `-to` variant on the staged path. `seal-inscription`, `seal-inscription-batch`,
`seal-recursive` and `seal-with-relationships` still mint to whoever seals.

---

## 3. Who ends up as what

| Role | `mint-single-tx` | `mint-single-tx-to` |
|---|---|---|
| Pays the protocol fee | `tx-sender` | `tx-sender` |
| Pays the miner fee | `tx-sender` | `tx-sender` |
| NFT owner | `tx-sender` | `recipient` |
| `InscriptionMeta.creator` | `tx-sender` | `recipient` |
| `payer` field on the event | `tx-sender` | `tx-sender` |

The recipient becomes **both owner and creator**. The payer appears nowhere in inscription
metadata, only on the emitted event.

**Post-conditions stay on the payer.** The fee still leaves `tx-sender`, so an existing
`<=` STX post-condition needs no change on the `-to` path.

## 4. Behaviour changes to check

### 4.1 Version string

```clarity
(get-contract-info) ;; version: "xtrata-v3.2.3"  ->  "xtrata-v3.2.4"
```

This is the most likely thing to break a working integration. If you branch on the version
string, add the new value.

### 4.2 The `inscription-sealed` event

One field added. Nothing removed, nothing renamed, no reordering.

| Field | v3.2.3 | v3.2.4 |
|---|---|---|
| `owner` | the minter | the **recipient** |
| `payer` | absent | **new.** the principal that paid |
| `event`, `token-id`, `token-uri`, `final-hash`, `chunk-size`, `total-size`, `total-chunks`, `dependencies`, `parents` | present | unchanged |

On a plain `mint-single-tx` the two fields are equal, so an indexer reading `owner` keeps
working. They only diverge on a `-to` call.

If your event parser rejects unknown fields, relax it.

One genuinely new event type: `parent-delegate`, with `owner`, `delegate`, `allowed`.

`inscription-migrated` and `upload-started` already exist in v3.2.3 and are unchanged. If
you index `inscription-migrated`, note only that `source-contract` can now also be
`.xtrata-v3-2-3`.

### 4.3 Upload expiry now runs on the burn chain

Only affects the staged path. If you only use single-tx, skip this.

| | v3.2.3 | v3.2.4 |
|---|---|---|
| Clock | `stacks-block-height` | **`burn-block-height`** |
| Constant | 4320 | 4320, unchanged |
| Real duration | **~15 hours** | **~30 days** |
| `UploadState.last-touched` holds | a Stacks height | **a Bitcoin height** |

The constant always claimed "~30 days at 10-min block cadence", which was true when one
Stacks block meant one Bitcoin block. Post-Nakamoto `stacks-block-height` advances every
~12.5 seconds, which silently cut the window to about 15 hours. Measured on mainnet across
39,000 blocks on 2026-08-04: mean 12.55 s/block, and a 4320-block window ranged 13.2 to
18.4 hours.

Pegging to the burn chain restores the documented meaning and stops it drifting again.

**What you need to change:**

- If you compute an expiry deadline off-chain, `last-touched` is now a **Bitcoin** height.
  Comparing it against a Stacks height will be wrong by a factor of about fifty.
- If you sized retry or resume windows around ~15 hours, you now have ~30 days.

Behaviour that has not changed: the window is rolling, refreshed by every
`add-chunk-batch`, so total upload duration is still unbounded. And an expired session
still cannot be resumed. Both `add-chunk-batch` and `begin-inscription` reject it with
`ERR-EXPIRED`, and recovery means purging indexes `0` to `total-chunks - 1` in batches of
50 before you can start over.

### 4.4 Limits

| Constant | v3.2.3 | v3.2.4 | Effect |
|---|---|---|---|
| `MAX-TOTAL-CHUNKS` | 2048 | **8192** | Max inscription 32 MiB -> 128 MiB |
| `MAX-TOTAL-SIZE` (derived) | 33,554,432 | **134,217,728** | |
| `CHUNK-SIZE` | 16384 | unchanged | |
| `MAX-SINGLE-TX-CHUNKS` | 32 | unchanged | Single-tx still caps at 512 KiB |
| `MAX-UPLOAD-BATCH-SIZE` | 32 | unchanged | |

A raise, so nothing that fit before stops fitting. Read these from `get-contract-info` at
runtime rather than hardcoding, and you get it for free.

## 5. Two assumptions that no longer hold

These are the ones worth reading carefully, because nothing will error. Your code will just
be quietly wrong.

### 5.1 Payer is no longer the owner

In v3.2.3 the principal that paid for an inscription was always its owner and creator. Any
logic that infers "who paid" from `get-owner` or `creator` was correct.

From v3.2.4, a `-to` mint breaks that. The only on-chain record of who paid is the `payer`
field on the `inscription-sealed` event. It is not stored in any map, so it is **not
readable after the fact** except by reading events.

If you need payer attribution, index the event at mint time. You cannot recover it later
from contract state.

### 5.2 A child's creator no longer implies parent ownership

In v3.2.3, `validate-parents` required `tx-sender` to own every parent, and `tx-sender` was
also the creator. So the creator of any child provably owned its parents at mint time.

In v3.2.4 a parent is accepted if **either**:

- the payer owns it (the v3.2.3 rule, unchanged), or
- the recipient owns it **and** that owner has delegated to the payer via
  `set-parent-delegate`.

Consequence: on a `-to` mint where the payer owned the parents, the child's creator is the
recipient, who never owned them. Do not infer parent ownership from `creator`.

**The anti-forgery guarantee is intact.** By default, only the owner of an inscription can
create children of it. A delegation is opt-in, specific to one delegate, revocable, and can
only produce children that mint to the owner, so it cannot be used to attach work to
someone else's lineage and keep it. If you are building on parent graphs, the property you
can still rely on is: **every child of an inscription was authorised by that inscription's
owner.**

## 6. What did not change

| Area | Status |
|---|---|
| Every v3.2.3 function signature and return type | Identical |
| All twelve error codes (`u100`-`u103`, `u107`, `u109`-`u115`) | **Identical.** No new codes, none reassigned. `set-parent-delegate` reuses `ERR-NOT-AUTHORIZED` |
| Fee units, formulas, and guards | Identical |
| `quote-inscription-fee`, `quote-staged-fee`, `quote-single-tx-fee` | Identical |
| Hashing, `process-chunk`, the incremental SHA-256 chain | Identical |
| `CHUNK-SIZE`, single-tx and batch limits | Identical |
| `transfer`, and the absence of an operator or approval pattern | Identical |
| Pause, allowlist, admin, ownership transfer | Identical |
| The staged path end to end | Identical |
| Dedup posture. No idempotency on mint, `existed` still literal `false` | Identical |
| SIP-009 surface | Identical |

**Idempotency is unchanged.** An identical re-mint from the same sender still succeeds with
a new token id and a second fee. Write your intent record before broadcasting, reconcile by
txid, and use `get-id-by-hash` as a free pre-flight check.

## 7. Migration semantics, if you consume migrated tokens

`migrate-from-v3-2-3` copies metadata and keeps the token id. It does **not** copy chunk
data. `get-chunk` and `get-chunk-batch` transparently proxy to the source contract, so
content reads work normally and you do not need to know a token was migrated.

| Property | Behaviour |
|---|---|
| Token id | Preserved |
| `creator` | Copied from the source. Original creator survives |
| `owner` | The migrating principal |
| Cost | `begin-fee-unit`, currently 100,000 microSTX |
| Old token | Transferred into the v3.2.4 contract, not burned |
| Content reads | Proxied. `get-chunk` returns the bytes as normal |
| Supported sources | `.xtrata-v1-1-1`, `.xtrata-v2-1-0`, `.xtrata-v3-2-3` |

v3.2.4 therefore depends permanently on those three contracts remaining readable. They are
immutable and reading is free, so this is a stated design consequence rather than a risk.

## 8. Notes if you are deploying against it

| | |
|---|---|
| Address | Must deploy from `SP3JNSEXAZP4BDSHV0DN3M8R3P0MY0EEBQQZX743X`. The `.xtrata-v1-1-1`, `.xtrata-v2-1-0` and `.xtrata-v3-2-3` references only resolve from there |
| Clarity version | **3.** Under Clarity 4 the contract fails to compile with `use of unresolved function 'as-contract'`, once per migrate function. Wallets default to 4, so deploy through the SDK |
| Verification | `contracts/clarinet/v3.2.4/` is a Clarinet project pinned to Clarity 3. `npm run test:v3.2.4` runs the compile check plus five suites: migration, composability, expiry, dedup, deploy order |

### Fees need no admin transaction

The fee defaults are set to what v3.2.3 charges on mainnet today, not the values v3.2.3
shipped with. `upload-chunk-fee-unit` is 1000 (was 2000) and `single-tx-fee-unit` is 10000
(was 100000). A one-chunk article quotes 11,000 microSTX from the moment it deploys, so
there is no window between deploy and correct pricing.

That also matters because `assert-valid-fee-update` caps one change at 10x down. Correcting
`single-tx-fee-unit` from 100000 to 10000 afterwards would sit exactly on that limit.

### `set-next-id` before anything mints. This one is unrecoverable

**The order is: deploy paused, `set-next-id` above the v3.2.3 ceiling, then unpause.**

`migrate-from-v3-2-3` mints a migrated token at the **same id** it had on v3.2.3, and
v3.2.4's `next-id` starts at 0. So a new inscription minted before `next-id` is raised takes
an id that a legacy token needs. That legacy token can then never be migrated, because ids
are unique and `set-next-id` refuses to run once anything has been minted.

Demonstrated in `xtrata-v3.2.4.deploy-order.test.mjs`:

| Step | Result |
|---|---|
| v3.2.3 holds token 0 | |
| A new v3.2.4 mint takes id 0 | |
| Migrate v3.2.3 token 0 | `ERR-DUPLICATE` (u114) |
| Rescue with `set-next-id` | `ERR-ALREADY-SET` (u115). No way back |

v3.2.3's last token id was 2975 on 2026-08-04 and it keeps climbing while unpaused, so pick
the ceiling after pausing v3.2.3, with headroom. Gaps in the id space are harmless.

## 9. Upgrade checklist

| | Check | Action if yes |
|---|---|---|
| 1 | Do you compare the `version` string? | Add `"xtrata-v3.2.4"` |
| 2 | Do you parse `inscription-sealed` with a closed schema? | Allow the new `payer` field |
| 3 | Do you hardcode 2048 chunks or 32 MiB? | Read `get-contract-info` instead |
| 4 | Do you infer the payer from `get-owner` or `creator`? | Index the event's `payer` field at mint time |
| 5 | Do you infer parent ownership from a child's `creator`? | Read `get-owner` on the parent instead |
| 6 | Do you call any v3.2.3 function? | No change needed |
| 7 | Do you rely on fee amounts or quotes? | No change needed. Keep quoting at runtime with `<=` post-conditions |
| 8 | Do you rely on mint idempotency? | It never existed. Reconcile by txid |
