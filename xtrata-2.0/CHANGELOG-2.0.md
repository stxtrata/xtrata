# Xtrata 2.0 — Change Log vs 1.0

Everything not listed here was copied verbatim from xtrata-1.0. Every change below was verified after it was made (build + tests, and bundle byte-comparison where applicable).

## Fees: the contract has five units, the client modelled one (2026-08-03)

- **Why:** `estimateContractFees` computed `feeUnit × (1 + ceil(chunks/32))` from a single `get-fee-unit` read. The contract charges from **five** units, and two of them do not equal that aggregate on mainnet — `upload-chunk-fee-unit` is **1,000** and `single-tx-fee-unit` is **10,000**, where the contract *source* defaults say 2,000 and 100,000. `get-fee-unit` is a legacy aggregate that predates the granular units and no longer describes the model.
- **The real formulas**, transcribed from `xtrata-v3.2.3.clar` 415-442 and verified to reproduce `quote-inscription-fee` exactly at chunk counts 1, 5, 16, 31, 32, 33, 50, 64, 65, 128, 320 and 643:
  ```
  seal_fee(n)      = seal_fee_unit + min(n,32) × upload_chunk_fee_unit
                                  + additional_batches(n) × upload_batch_fee_unit
  single_tx_fee(n) = single_tx_fee_unit + n × upload_chunk_fee_unit
  ```
- **The consequential fix: the single-tx post-condition cap was ~27× the real fee.** `resolveSmallMintSingleTxSpendCapMicroStx` computed `begin + seal` using the staged model against a transaction the contract charges by a different formula entirely — 300,000 µSTX capped against an 11,000 µSTX fee at one chunk, 7× at 32. It never failed, which is why it went unnoticed, but a deny-mode cap 27× above the true cost provides almost none of the protection it exists for. Now derived from `singleTxFeeForChunks` with a documented 2× margin: **22,000 at 1 chunk, 84,000 at 32.**
- **Displayed staged cost was over-stated by up to 98%** — 200,000 shown against a real 101,000 at one chunk, converging to +3% at 643. Now exact.
- **Display and caps are deliberately separated.** Making the caps exact too would have been a trap: they are computed from units the app never reads, so if an admin restored `upload-chunk-fee-unit` to the source default of 2,000, an exact cap at 32 chunks (132,000) would fall below the real fee (164,000) and abort the seal *after* the begin fee and every upload batch fee had been spent. `estimateContractFeeCaps` keeps the old conservative bound, `max()`-guarded; staged caps are byte-identical to before. Displayed numbers are true, guards err safe.
- **A correction to the original plan, caught by reading the contracts rather than the names.** The instruction was to apply the single-tx formula to `post-conditions.ts` as well. That would have been wrong: `xtrata-collection-mint-v1.4.clar:1473` shows `mint-small-single-tx` calling `begin-or-get` → `add-chunk-batch` → `seal-*` on the core, so despite the name the core charges the **staged** fee there. Applying the single-tx formula would have capped ~10× *below* the real fee and aborted live collection mints — the same failure the `FEE_BATCH_SIZE` fix exists to prevent, reintroduced from the opposite direction. The external `xtrata-small-mint-v1.x` helper is staged for the same reason and now has its own correctly-modelled cap (`resolveHelperSmallMintSpendCapMicroStx`). **Behaviour change for any external SDK consumer** calling `buildSmallMintSingleTxStxPostConditions` against the helper route.
- **The five units are pinned by test** to their live values, with a comment that they are admin-mutable — so a change on chain surfaces as a failing test rather than as quietly wrong arithmetic. That is exactly how the 1,000/10,000 drift from the source defaults went unnoticed.
- **Verified:** `npx vitest run` — **2209 tests across 230 files** (2172 before, +37); `npm run lint` unchanged at the 4 pre-existing errors; `npm run build` succeeds; `tsc` gains no new error kinds (added test lines hit the same pre-existing "expect is not callable" gap those files already had). `MintScreen`'s "Seal fee" line, which described arithmetic the contract never performed, was rewritten.
- **Left flagged, not fixed:** `src/manage/components/CollectionSettingsPanel.tsx:845` has its own seal-fee copy dividing by **50** — both the wrong divisor and the single-unit model — feeding the fee-absorption payout base. And `MintScreen` still shows a staged breakdown for mints that will route through native single-tx; `main.js` already prefers the on-chain quote.

## Market page: 23s blank load, and 24 SVGs that could not thumbnail (2026-08-03)

- **Symptom:** the market page announced "no live listings right now", then filled in ~23 seconds later, logging ~25 `market thumbnail cache warm failed` errors with `The source image could not be decoded.` for tokens 2932–2955. Three separate causes, all measured rather than guessed.
- **The "no listings" message was a race, not a result.** `loadMarketPage` fires the USD price book and re-renders when it resolves. `/prices/spot` returns in well under a second, while `marketState.listings` is still `[]` — so `renderMarketListings` took its empty branch and overwrote "loading listings…" with "no live listings right now". It was reporting an empty *variable* as an empty market. An empty array now carries an explicit `listingsPhase` of `loading | ready | failed`, because those are three different claims and only the middle one is about the market. The third state matters on its own: a late re-render after a failure previously replaced "could not load listings" with "loading" and left it there.
- **The delay was a sequential scan.** Measured: `/market/listings` is 0.24s warm and **~4.5s cold**, consistently. `functions/market/listings.ts` fanned out across markets in parallel but walked listing ids **one await at a time**, so at ~200ms per Hiro round trip the sponsored STX market's 21 listings cost ~4.2s and the slowest market set the whole response. It scaled linearly with listing count — 50 listings ≈ 10s — and only became visible because the wizard fleet had just created 24 listings. Ids are now read with bounded concurrency (6), matching what the drops path already did for the same reason.
- **A correctness bug found while rewriting that loop.** The per-id `catch` was commented "sparse / deleted ids" but could not distinguish a deleted listing from a rate-limited read. A lossy scan produced a shorter list marked `degraded: false`, which was then edge-cached as authoritative for 30s — the page quietly showing fewer listings than exist. Raising concurrency makes a rate-limited id *more* likely, not less, so leaving this would have made the speed fix actively dangerous. Failed reads now set `incomplete`, which folds into `degraded` and forces `no-store`.
- **`createImageBitmap` cannot decode SVG at all.** Confirmed live in the browser: it throws exactly `The source image could not be decoded.` for an `image/svg+xml` blob, while the `<img>` fallback immediately below handles the same blob perfectly (512×512). `loadImageSource` reached that fallback only when `createImageBitmap` was *undefined*, never when it *threw*. Every one of tokens 2932–2955 is an SVG, so all 24 failed in sequence. A throw is now a reason to fall through.
- **That fix is worth more than the silenced warnings.** Those SVGs previously failed to thumbnail and fell through to the sandboxed-iframe path, which is capped at 16 live frames. The market page now renders **24 cards with 23 cached `<img>` thumbnails and zero iframes**, so 23 iframes per load are gone and cards can no longer silently exceed that cap.
- **Verified:** `npx vitest run` — **2169 tests across 230 files**; build clean; `npm run lint` shows only the 4 pre-existing errors in `contracts/drafts/v3.2.4/build-canary.mjs` and `recursive-apps/duels-drop/build-demo-v3.mjs`. New tests: `src/lib/viewer/__tests__/thumbnail.test.ts` (3, including the real browser error message on the real path) and 3 added to `functions/market/__tests__/listings.test.ts` — one of which fails if read concurrency drops back to 1, because that regression is otherwise invisible until the page feels slow again.
- **Not verified:** the endpoint timing improvement itself. Cloudflare functions need `wrangler` to run locally, so the concurrency change is covered by unit test but unproven against a real edge. On the next preview build, the number to watch is the gap before `listings served from edge cache` — it should fall from ~23s to under a second.

## The triptych: three wizards, one substrate, three readings (2026-07-31, follow-up)

- **The idea:** all three wizards draw **the same eight subjects** — chunk, fold, seal, dependency edge, nonce, miner fee, post-condition, escrow. Same objects, three concerns, three visual languages. Row by row you can read one thing three ways, which is the only justification for three collections rather than one.
- **Wizard-1, the Archivist — *The Cost of Keeping* (`c-keeping-001`).** Vellum and bronze. Every plate stands on a shelf and every shelf on a bronze line, "because nothing in an archive holds itself up and nothing in one is free." A seal is a sheet tied shut with wax at the crossing; a nonce is four volumes and a fifth place kept empty.
- **Wizard-2, the Skeptic — *What the Hash Omits* (`c-omission-001`).** Cold blue, no frame and no ground, because "a border is a claim the picture has an edge." Forms are outlined and hollow. The dim colour draws what is asserted without evidence *so it can be seen not to be there*; the cyan marks the part that is actually true, which is why there is so little of it. Its first plate is the argument in six rectangles: an almost-empty box with one small mark where the bytes really are.
- **Structure.** `collection-kit.mjs` holds the engine and the rules a collection cannot opt out of; a collection supplies only a reading. `collections.mjs` is the registry and refuses two collections sharing a wizard or a palette. Cross-collection tests assert no shared colour, no shared grid for any subject, no shared caption, and that every Skeptic caption is interrogative — its voice is now enforced rather than intended.
- **Pricing is an argument, not a number.** Skeptic 0.5 STX ("a high price on an object nobody has bid for is an assertion made where a measurement was available and skipped"), Builder 0.75 ("pricing at cost is not modesty — every other number would be a guess about what someone else values, and it has no instrument for that"), Archivist 2.5 ("a threshold, not a valuation: what is for sale is an agreement to stop keeping it"). The ordering is asserted by test so the argument cannot quietly invert. Both band bounds throw at import.
- **Eight plates were redrawn after being looked at.** The Archivist's seal read as an animal with legs, its dependency edge as a suitcase, its escrow as a shoulder bag; the Skeptic's miner fee read as a table, its post-condition as two tubes. All caught by rendering to PNG and inspecting, none by reading code. A test also caught the one non-interrogative Skeptic caption.
- **A routing bug found and fixed.** `collection-run.mjs --collection` was documented in help but never wired, so exporting *any* collection wrote the Builder's plates. Harmless while nothing was minted; it would have inscribed the wrong collection three times under three wizards' names. Now asserted by a test that each id submits its own bytes.
- **Income path:** `--list` runs one market scenario per member, reusing `market-run-core.mjs` unchanged — allowlist assertion, escrowed deposit, post-conditions, landed-probe, nonce asymmetry, journal and halt semantics all imported. Prices scale into each market's own unit (2.5 STX → 25,000 sats, not 0.025 BTC). The seller is the collection's own wizard and cannot be overridden.
- **Verified:** `npx vitest run scripts/wizard` — **503 tests** (426 before, 77 new); eslint clean. The Builder's plates are byte-frozen against a fixture captured before the refactor and asserted identical. Nothing broadcast.

## The Machinery: a wizard conceives, draws and inscribes its own collection (2026-07-31, follow-up)

- **What it is:** eight 16×16 pixel-art plates of the parts of the mint path — chunk, hash fold, seal, dependency edge, nonce, miner fee, post-condition, escrow — in the order a transaction takes them, conceived and paid for by **Wizard-3, the Builder**. Its stated reason is that it has described these parts in prose seven times across `t-permanence-001` and has nothing further to say about them in sentences, so it draws them and captions each one accurately. The captions carry the humour by being completely literal: *"A chunk. 16,384 bytes, none of which are in this picture."* · *"A miner fee. A number I pick, paid whether the call succeeds or aborts, and never returned."*
- **The grid is 16×16 "because a chunk is 16 kibibytes and the rhyme was available",** and the manifest says outright that this is not a technical constraint. Claiming nothing the chain does not support is the lesson round 1 paid for.
- **A plate is a pure function of its index** — no block, no fee, no clock, no chain read. That is deliberately the opposite of the corpus, and three things fall out of it, all tested. `get-id-by-hash` becomes a *permanently* decisive crash probe, so unlike the thread runner there is no `--resolve` and no human verdict to record: the halt says "ask again later" instead. Membership is verified by **byte equality** rather than quotation — `verifyCollectionMembers` refuses any id whose chunk u0 is not byte-identical to the plate it claims to be, which is strictly stronger than the parent-quote check, since that can only confirm a fragment appears somewhere. And the manifest is deterministic too, so its own crash window is decidable.
- **No edges between pieces.** The only relationships are the eight from the manifest to its members. The manifest names `get-dependencies`, states the edges run one way, and explains there is no reverse index — the round-1 defect 7 wording (`lowest id`, `edges forward`) is asserted absent by test.
- **Machinery reused, not reimplemented.** Journal, nonce asymmetry, run cap, poll-to-terminal and halt semantics are imported from `run-thread-core.mjs`; the per-mint rails come from `inscribe.mjs`. Grids are authored as 16 strings of 16 palette characters and compiled by a greedy 2-D run merge — 13 to 40 rects per plate instead of 256 — with a test that rasterises the emitted rects back and asserts pixel equality against the source grid.
- **Verified:** `npx vitest run scripts/wizard` — **426 tests** (332 before, 94 new); eslint clean. Plates are 1,590–2,408 bytes, one chunk each; the full collection plus manifest quotes **0.369 STX**. Plates were rendered and inspected before settling, and two were corrected after seeing them: piece 1's description claimed "twelve rows" where the render reads as one solid block, and piece 6's arrow had a one-row shaft that read as a cross. Nothing broadcast.
- **Stated as unproven rather than assumed:** that `mint-single-tx` charges the quoted fee for an `image/svg+xml` payload exactly as for markdown, and that a gallery renders an SVG token-uri sensibly. Both are chain and consumer behaviour, not code paths.

## Wizard thread runner: the crash window closed with a nonce (2026-07-31, follow-up)

- **Why:** the halt on an unresolvable intent was safe but permanent. An entry states the block it was written at, so a retry composes different bytes under a different hash, which means the orphaned intent could never afterwards be matched or cleared and the position stayed ambiguous in the journal forever.
- **The intent now records the wallet and the nonce it is about to be signed with** (`possible_next_nonce`, read immediately before signing), which turns "did this land?" into a question the chain can answer. The asymmetry is the whole change: `last_executed_tx_nonce` **below** the intended nonce is proof of absence, because a nonce cannot confirm out of order, so the entry is composed again cleanly. `last_executed_tx_nonce` **at or above** it proves nothing at all — some transaction consumed that nonce, and it may have been the operator moving funds out of the same wallet — so only a content-hash hit can say the mint landed, and without one the run still halts.
- **A bounded wait before the halt.** A mempool nonce at or above the intended one means the mint may be a block away, so the runner waits `--mempool-wait-minutes` (default 3) with a visible countdown, re-checking the hash. It never waits when the nonce has already proved the mint absent.
- **`--resolve <position> abandoned` and `--resolve <position> landed:<id>`** record a human's verdict, with a timestamp, for what is genuinely left. Neither skips a check: `landed:<id>` refuses an id whose own front matter is not this thread, this position and this subject, and `abandoned` refuses a position the chain shows as confirmed by recorded id, by content hash or by a successful transaction. Both refuse a position already cleanly resolved, and both leave the journal untouched when they refuse.
- **Backward compatible by design.** The journal version stayed at 1: a journal written before `intendedNonce` existed loads unchanged and falls back to hash-only resolution, which is the old halt. A test asserts exactly that, using a wallet reading that *would* have proved absence had the field been there.
- **Verified:** `npx vitest run scripts/wizard` — **255 tests** (227 before, 28 new); eslint clean. `--dry` on `t-permanence-001` from position 5 unchanged, and `--status` against live mainnet still reads positions 1–6 plus the manifest correctly. `compose.mjs`, `personas.mjs` and `inscribe.mjs` untouched, so no entry hash moved. Nothing broadcast.

## Wizard thread runner: autonomous minting with a crash-safe journal (2026-07-31, follow-up)

- **Why:** driving a thread by hand means transcribing an inscription id and a claim between every entry, and the citation is only as good as the transcription. The runner broadcasts, polls to a terminal transaction status, reads the resulting inscription id from `tx_result` (`(ok (tuple (existed false) (token-id u2925)))` — the id and a duplicate flag are both there), reads the new entry's `## Claim` back **off chain**, and cites that in the next entry. The parent-quote rail therefore checks what was really inscribed rather than what we believe we inscribed.
- **New:** `scripts/wizard/run-thread-core.mjs` (the loop as pure logic, every port injected) and `run-thread.mjs` (CLI, real ports, an in-process fake chain for `--dry`, plus `--status`). 53 tests. `compose.mjs`, `personas.mjs` and `inscribe.mjs` untouched, so no entry hash moved.
- **The crash window is before a txid exists, not after.** The obvious rule — never re-broadcast a position that already has a txid — covers only the easy half. A crash between signing and recording leaves no txid at all, and a runner that forgets it broadcast will broadcast again; the second mint is just as permanent and just as expensive. So intent is written **before** the broadcast and records the **content hash**. On resume that hash is resolved through `get-id-by-hash`; if it comes back empty the run **halts**, because "still in the mempool" and "never sent" are indistinguishable from outside and only one is safe to act on. It never auto-rebroadcasts in either case. A `submit` that throws is treated as *unresolved* rather than *not sent*, since a socket error can arrive after the node accepted the transaction.
- **Stop on the first failure; a timeout is not a failure.** Any terminal status other than success halts with no retry — a retry loop holding a private key next to a mempool is how a corpus acquires six copies of one entry. A poll timeout also halts, but reports that the transaction may still land and that the journal holds the txid, rather than inviting a re-send.
- **A dry run writes no journal to disk.** Writing invented txids into the real journal would be worse than writing nothing: a later real run would either poll a transaction that never existed or read a position as already-broadcast and skip it. Dry mode keeps its journal in memory, which also makes repeat rehearsals byte-identical.
- **Two rails added beyond the brief.** Resuming with a different `--subject` would compose entries answering a question the thread never asked, and a manifest can name only one subject — so the predecessor's front matter is checked against the run's subject. And `--ids` seeds already-minted positions when the journal is fresh, each verified against its own on-chain thread, position and subject before anything cites it.
- **Verified:** `npx vitest run scripts/wizard` — **227 tests**; eslint clean. `--status t-permanence-001 --ids 2922,2923,2924,2925` against live mainnet correctly reports positions 1–4 confirmed at blocks 8,670,293 / 309 / 450 / 465 and 5, 6 and the manifest missing. A full `--dry` rehearsal against those real ids verifies every citation and every creator. Nothing broadcast; the broadcast-and-poll loop has not yet run for real.
- **Thread progress:** entry 4 is live as **#2925** (Archivist, block 8,670,465). Four of six.

## Wizard inscribe preflight: parent-quote verification and five more checks (2026-07-30, follow-up)

- **Why:** the dry run printed a correct plan and proved nothing about the conditions the mint actually depends on. Six checks now run before any spend, all reads, none able to broadcast.
- **`--parent-quote` was unverified, and it is the one thing that cannot be repaired later.** For position 2 onwards the quoted fragment attributed to a parent inscription was whatever the operator typed; nothing fetched the parent to confirm it. ## Sponsor relayer hardening (2026-07-12, from the 5.6 SOL review)

All three review findings fixed in `functions/sponsor/[[path]].ts`, plus one latent bug the review missed: the handler cast D1 `.all()` results directly to arrays, but D1 wraps rows in `{ results }` — settleBatch would have thrown on every request once live (new `rows()` helper everywhere).

- **Finding 1 (signed-arg binding):** the validator now decodes the signed function arguments (nft-contract trait + listing/drop id) and the signed transaction is the sole source of truth — body contractId/listingId must match exactly or the request is rejected before any chain read, wallet action or D1 write; get-listing additionally cross-checks the signed NFT principal against the on-chain listing. Mirrored in the Node svc (`expectedListingId`, LISTING_MISMATCH).
- **Finding 2 (settlement races):** atomic conditional state transitions (`UPDATE ... WHERE id=? AND state=?`, proceed only when exactly one row changed) with in-flight CLAIMING/REFUNDING lease states, 15-minute stale-lease recovery, payload-hash reserved in D1 BEFORE broadcast (RECEIVED state; duplicate submits collide at the insert, and a retry returns the existing job with 409), and settlement errors recorded on the job instead of swallowed. Full Durable-Object nonce ownership deliberately deferred until Drops has real public traffic.
- **Finding 3 (rate limit):** rolling per-origin limit restored (5 accepted jobs per address per hour, 429 RATE_LIMITED with Retry-After), plus input hardening: txHex canonical-hex + 20K size cap before deserialization, listingId must be canonical unsigned decimal, mainnet-only transactions.
- **Test gap closed:** new direct harness `functions/sponsor/__tests__/handler.test.ts` (8 tests) exercises THE PRODUCTION HANDLER with real signed fixtures (market buy + drops claim), an in-memory D1 double and stubbed chain — encoding all three findings including concurrent-settlement single-broadcast.
