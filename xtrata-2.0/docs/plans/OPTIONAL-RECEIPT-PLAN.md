# Plan — make the on-chain receipt optional (off by default)

## What the "receipt" actually is
After the file is inscribed and delivered, the agent mints a **second on-chain
single-tx inscription**: an HTML receipt (`inscribeReceipt`, ~1 chunk /
`RECEIPT_SIZE_EST` 9000 bytes) that depends on the file token + the agent
identity, then transfers that receipt token to the recipient. It costs real
money — `receiptProtocol + receiptMiner` (~0.1 STX protocol + a miner reserve) —
and that cost is **baked into the deposit** the user is asked to pay.

So "make the receipt optional, off by default" means:
1. Stop minting/delivering that second inscription unless the user opts in.
2. Stop charging for it — the deposit should drop by the receipt cost when off.
3. A prominent top-level toggle, unchecked by default.

### DECIDED (Jim): always generate, inscribing is optional
The receipt **HTML is always generated and saved locally** (free, off-chain) so
it can always be viewed via "View receipt". The **toggle only controls whether
that receipt is also inscribed on-chain** (the extra mint + delivery + cost).
Default: on-chain receipt OFF. So `job.receipt` specifically means *"inscribe the
receipt on-chain"*, not *"produce a receipt at all"*.

## The one thing that makes this fiddly
The receipt logic exists **twice**, and both are live:
- `src/agent-one/agent-core.ts` — the browser bundle (`window.XtrataAgent`).
  **This is what the backendless wizard runs.** Compiled to `agent-one.js`.
- `xtrata-agent-one/svc/core.mjs` — the Node CLI / deposit-service path.

Every change below is made in **both** files, kept byte-compatible in behavior,
then `agent-one.js` is rebuilt (Linux esbuild). `dist/wizard` is regenerated by
the `postbuild` copy step, so no hand-syncing there.

## Data model
Add one boolean to the job: `job.receipt` (true = mint the on-chain receipt).
- New jobs from the updated wizard pass `receipt:false` by default.
- **Backwards compatible:** treat only `job.receipt === false` as "off".
  Existing in-flight/old jobs have no field → `!== false` → they still get the
  receipt they already budgeted for. No funded job breaks.

## Changes

### 1. Cost estimate — exclude the receipt when off (both cores)
`estimate()` / `estimateBatch()` gain a `receipt = true` param. When false:
```
receiptProtocol = 0n; receiptMiner = 0n;   // before baseCosts is summed
```
`baseCosts` then omits the receipt, so `requiredUstx` (the deposit) drops by the
receipt cost. The returned `receiptProtocol/receiptMiner` are `'0'`, which keeps
all downstream reconciliation maths (`receiptData`, `reserveAhead`) correct.

### 2. createJob / createBatch — store the flag (both cores)
Accept `receipt` (default `true` in core to protect the CLI/tests), thread it
into the estimate call, and persist `job.receipt = receipt !== false`.

### 3. deliverJob / deliverBatch — skip the mint when off (both cores)
Wrap the receipt inscription + its delivery in `if (job.receipt !== false)`:
- **On (or legacy):** unchanged — mint receipt, deliver it, save HTML.
- **Off:** skip `inscribeReceipt` and the receipt `sendNft`; `receiptTokenId =
  null`; guard the `r.minerFee` reference. The change sweep already returns
  everything left over, so skipping the receipt simply means **more change comes
  back** — the critical file delivery and refund paths are untouched. This is
  the safe part: nothing about the user's actual inscription changes.
- **Local summary:** still write the free local HTML summary (`saveReceiptHtml`
  with `receiptTokenId:null`, which already renders as "this inscription"), so
  "View receipt" keeps working and the user still has an off-chain record. (This
  is a small decision — see below; alternative is to skip it entirely.)

### 4. Completion UI copy (wizard)
The done-card currently says "inscription + receipt delivered". When
`job.receipt === false`, drop the "+ receipt" wording so it reads "inscription
delivered, change refunded". Hide/relabel the "View receipt" button accordingly
if we skip the local summary.

### 5. Top-level toggle (wizard `index.html`)
A prominent checkbox near the top of the form (not buried in Advanced options),
e.g. above the drop zone / next to the header — **"Inscribe an on-chain receipt
(+~0.1 STX)"**, unchecked by default. Behavior:
- Persist the choice to `localStorage` so it sticks between visits.
- On change, re-run the active quote (single **and** batch) so the displayed
  cost updates immediately.
- Thread the value into both estimate calls (single ~L999, batch ~L759) and both
  create payloads (single ~L1046, batch ~L854).

### 6. Rebuild + verify
- Rebuild `agent-one.js` via the Linux esbuild against repo node_modules.
- `node --check` both cores + the wizard inline script.
- Extend the existing deliver-routing vitest: one mock job `receipt:false`
  (asserts no receipt mint, `receiptTokenId` null, deposit lower) and one
  `receipt:true` (unchanged), plus a legacy job with no field (still receipts).

## Safety summary
- The receipt is a *post-delivery, best-effort* step today; removing it can't
  affect whether the file inscription succeeds or whether change is returned.
- Cost only goes **down** when off; any estimate rounding just returns as change.
- Legacy jobs are explicitly preserved via the `!== false` default.
- Two-core parity + bundle rebuild is the only real footgun — hence both files
  change together and the vitest asserts parity.

## One decision left to confirm
- **CLI/service default:** leave `svc/core.mjs` defaulting to on-chain receipt
  **on** (only the wizard defaults off), or flip the whole system to
  off-by-default? (Decision 1 — local summary — is settled: always generate it.)
